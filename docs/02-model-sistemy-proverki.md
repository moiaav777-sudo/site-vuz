# Модель системы мониторинга сайта вуза

Цель: регулярно проверять официальный сайт вуза (и связанные домены) на соответствие законодательству, доступность, целостность данных и внешние угрозы, и на выходе давать документ того же класса, что «панель руководителя» v2, но с вычислимыми оценками, доказательствами и историей.

## 1. Границы объекта проверки

| Контур | Что входит | Примечание |
|---|---|---|
| Основной портал | pnzgu.ru, www.pnzgu.ru, раздел /sveden | обязательный раздел по ст. 29 ФЗ-273 |
| Поддомены | всё из crt.sh и DNS (elib, lms, mail, филиалы) | инвентаризация раз в неделю |
| Филиалы | kiiut.ru, sfpgu.my1.ru и др. | те же проверки, что и для портала |
| Внешние регистры | fgosvo.ru, реестр лицензий, WHOIS, crt.sh | только как источники истины для сверки |

Проверки только пассивные и неинвазивные: GET/HEAD-запросы с ограничением скорости, чтение публичных страниц, публичные базы. Активное сканирование уязвимостей (nuclei, nmap, перебор путей) включается отдельным модулем только по письменному разрешению ректора/ЦНИТ.

## 2. Шесть фронтов проверки

### Фронт A. Обязательная информация (ст. 29 ФЗ-273, ПП №1802, приказ Рособрнадзора №1493 в ред. №920)
- Наличие всех подразделов /sveden и их URL-имён по п. 6 №1493.
- Наличие каждого обязательного поля и микроразметки `itemprop` по пп. 7–20 (п. 27).
- Машиночитаемость таблиц (п. 26): рядом с HTML есть CSV/XLSX/JSON либо таблица корректно парсится.
- Срок обновления ≤10 рабочих дней (ч. 3 ст. 29 ФЗ-273, ПП №1802): считается только при доказанном изменении — сверка с предыдущим снимком и внутренним журналом.
- Новые нормы с датой вступления: подп. «о» п. 1 ч. 2 ст. 29 (комнаты для студенческих семей, с 01.09.2026) и последующие.
- Документы: формат (PDF/ODT/DOCX), читаемость текста (не скан без OCR), наличие ЭП там, где сайт заявляет «подписано».

### Фронт B. Доступность (ПП РФ №102 от 07.02.2026, ГОСТ Р 52872-2019, ПП №1802)
- Масштабирование текста до 200% без горизонтальной прокрутки; отсутствие `maximum-scale`/`user-scalable=no`.
- Автоматический прогон axe-core по всем шаблонам страниц: alt, заголовки, контраст, фокус, язык страницы.
- Версия для слабовидящих: наличие и работоспособность.
- Документы читаемы экранным диктором (текстовый слой в PDF).

### Фронт C. Персональные данные и информация (152-ФЗ, 149-ФЗ)
- Политика обработки ПДн опубликована и доступна с каждой формы (ч. 2 ст. 18.1 152-ФЗ).
- Формы: только https, есть согласие на обработку.
- Иностранные счётчики, шрифты, капчи, встроенные видео: перечень и признак трансграничной передачи.
- Авторизация пользователей (ЛК, LMS) только через российские сервисы (требования 149-ФЗ).
- Хостинг: провайдер в реестре Роскомнадзора, IP в РФ.
- Реестр ППС: публикуются только поля, требуемые п. 12 №1493, без лишних ПДн.

### Фронт D. Безопасность внешнего периметра (пассивно)
- TLS: срок, цепочка, протоколы, HSTS; срок домена по WHOIS; DNSSEC.
- Заголовки: CSP, X-Frame-Options, X-Content-Type-Options, Referrer-Policy.
- Почта домена: SPF, DKIM, DMARC (защита от фишинга от имени вуза).
- Инвентаризация поддоменов (crt.sh, DNS) и их живость; заброшенные поддомены и CNAME на чужие сервисы (subdomain takeover).
- Отпечаток CMS/серверного ПО и известные CVE по версии (без эксплуатации).
- Чёрные списки: Яндекс Safe Browsing, Google Safe Browsing, VirusTotal.
- Контроль подмены контента: хэш и текстовый diff главной и /sveden между обходами; поиск вставленных `<script>`/`<iframe>` с чужих доменов внутри контентных полей (кейс ИнОУП).
- Открытые служебные пути по короткому списку (админка CMS, `.git`, бэкапы) только на факт ответа 200.
- Домены-двойники (typosquatting) по crt.sh и DNS.
- Доступность с двух маршрутов: российский egress и внешний.

### Фронт E. Целостность данных и ссылок
- Живость каждой ссылки по телу ответа (soft-404), не по коду.
- Ссылки на ФГОС: код направления в подписи = код в имени файла = запись реестра fgosvo.ru.
- Пары «PDF + .sig»: наличие и криптографическая проверка подписи (ГОСТ, через КриптоПро CSP или openssl-gost).
- Согласованность фактов между страницами и сайтами: ФИО руководителей, названия подразделений, адреса.
- Мусор в данных: HTML/скрипты в текстовых полях, битые строки выгрузок.

### Фронт F. Качество площадки (не нормы, справочно)
- sitemap, robots, canonical, редирект www, HTTP/2, IPv6, время ответа.

## 3. Архитектура

```
[Реестр норм и проверок]        [Расписание]
   rules/*.yaml  ─────┐              │
                      ▼              ▼
              ┌──────────────────────────────┐
              │ 1. Сборщик (crawler)         │  Playwright + httpx, RU-egress,
              │    снимки HTML/заголовков/   │  лимит скорости, повторы
              │    PDF/.sig → хранилище      │
              └──────────────┬───────────────┘
                             ▼
              ┌──────────────────────────────┐
              │ 2. Экстракторы               │  itemprop, таблицы→CSV,
              │                              │  PDF-текст, метаданные, DNS/TLS
              └──────────────┬───────────────┘
                             ▼
              ┌──────────────────────────────┐
              │ 3. Детерминированные чекеры  │  90% проверок: код на Python,
              │    → findings (JSON)         │  каждое с evidence_id
              └──────────────┬───────────────┘
                             ▼
              ┌──────────────────────────────┐
              │ 4. LLM-аналитик (Claude)     │  только там, где нужно суждение:
              │    structured outputs        │  содержание PDF, классификация
              │                              │  дефектов, формулировка «что делать»
              └──────────────┬───────────────┘
                             ▼
              ┌──────────────────────────────┐
              │ 5. Скоринг и дельта          │  формула по фронтам, сравнение
              │                              │  с прошлым запуском, алерты
              └──────────────┬───────────────┘
                             ▼
              ┌──────────────────────────────┐
              │ 6. Генератор отчётов         │  JSON → HTML-панель (как v2),
              │                              │  PDF для руководства, CSV/JSON
              └──────────────────────────────┘
```

### 3.1. Реестр норм и проверок
Каждая проверка описана в YAML (см. `rules/checks.yaml`): идентификатор, норма с пунктом, дата вступления в силу, фронт, тип (автомат / LLM / ручная), класс результата (нарушение / риск / проверить / факт), какое доказательство обязательно. Изменение закона = правка YAML с датой, без правки кода. Отдельный «нормативный монитор» раз в неделю ищет новые редакции №1493, №1802, ст. 29 ФЗ-273, ПП №102 и заводит задачу юристу.

### 3.2. Сборщик
- Обход по карте обязательных URL из реестра плюс обнаруженные ссылки глубиной 2 внутри /sveden.
- Каждый ответ сохраняется целиком: URL, заголовки, тело, хэш, время, маршрут (RU/внешний). Это неизменяемое доказательство, на которое ссылаются все находки.
- Определение soft-404 по эталону тела (длина, фраза «Ошибка 404», отсутствие Last-Modified у «PDF»).
- Ограничение: не более 2 запросов в секунду на хост, User-Agent с контактом.

### 3.3. Детерминированные чекеры
Пишутся как функции «снимок → список findings». Пример находки:

```json
{
  "check_id": "A-07-fgos-code-match",
  "status": "violation",
  "severity": "high",
  "norm": "ч. 1 ст. 29 ФЗ-273; п. 15 Требований №1493 (ред. №920)",
  "where": "/sveden/eduStandarts",
  "object": "37.04.01",
  "message": "В подписи код 37.04.01, файл 380401.pdf",
  "evidence": ["snap:2026-09-29:eduStandarts#row-118"],
  "fix": "Заменить ссылку на файл ФГОС 37.04.01 из реестра fgosvo.ru",
  "owner_role": "Проректор по учебной работе",
  "first_seen": "2026-09-29",
  "last_seen": "2026-09-29"
}
```

### 3.4. LLM-аналитик
Куда LLM действительно нужна (и где обычный код не справится):
- Прочитать PDF положения и ответить, содержит ли оно требуемые нормой сведения (например, положение о жилье — порядок предоставления изолированных помещений семьям).
- Сопоставить текст страницы с перечнем обязательных полей, когда микроразметки нет.
- Классифицировать дефект ссылки (не тот файл / чужой источник / формальный дефект) по содержимому.
- Сверить факты между портал и сайтом филиала (ФИО, должности).
- Сформулировать карточку «что делать / кому / срок» на основе находки и нормы.
- Собрать текст блока «дельта к прошлой версии».

Правила использования:
- Модель по умолчанию: Claude Opus 5.5 (`claude-opus-5-5`), адаптивное мышление, `output_config.effort: "high"` для правового анализа. Для массовой выгрузки полей из тысяч страниц и PDF — Claude Haiku 4.5 (`claude-haiku-4-5`) через Batch API (вдвое дешевле, ответ в течение суток). Если нужна максимальная точность на спорных юридических вопросах — Claude Fable 5.1 (`claude-fable-5-1`) точечно.
- Только structured outputs по JSON-схеме находки; ответ без `evidence` отбрасывается.
- LLM не присваивает статус «нарушение» сама: она возвращает факт и уверенность, статус ставит правило из реестра.
- Реестр норм и схема кладутся в кэшируемый префикс запроса (prompt caching), тексты страниц — после него.
- Все запросы и ответы модели логируются рядом со снимком как часть доказательной базы.

Ориентир стоимости: Opus 5.5 — 4 $/млн входных и 20 $/млн выходных токенов; Haiku 4.5 — 1 $/млн и 5 $/млн; Batch API даёт скидку 50%. Полный обход /sveden ПГУ (≈800 документов) с чтением всех PDF через Haiku в батче укладывается в единицы долларов, аналитический слой на Opus — в десятки долларов за отчёт.

### 3.5. Скоринг
- Каждая находка имеет вес по классу: нарушение 1,0; риск 0,5; проверить 0,2; факт 0.
- Оценка фронта = 100 × (1 − Σ весов найденного / Σ весов всех проверок фронта), ограничено [0; 100].
- Индекс = взвешенное среднее фронтов: A 0,35; B 0,15; C 0,15; D 0,20; E 0,15; F не входит в индекс.
- Формула публикуется в отчёте; изменение весов версионируется.

### 3.6. Дельта, история, алерты
- Находки сопоставляются по `check_id + object`: новые, закрытые, регресс.
- Алерты немедленно (почта/Telegram/Max): сертификат < 30/7/1 дня, домен < 30 дней, изменение хэша главной вне окна публикаций, новый чужой скрипт в контенте, домен в чёрном списке, недоступность > 15 минут с RU-маршрута, смена ФИО ректора/проректоров.
- Ежедневно: лёгкий прогон (живость, TLS, дефейс, чёрные списки).
- Еженедельно: полный обход и отчёт-дельта.
- Ежемесячно и по запросу: полный документ для руководителя.

### 3.7. Отчёт
Единый JSON результата → три представления:
1. HTML-панель (тот же формат, что v2: итог, фронты, карточки решений, полные данные, построчные таблицы, пробелы, план, методика, реестр цифр, дельта). Все числа в тексте генерируются шаблоном, рукописных цифр нет.
2. PDF/DOCX для официального оборота с датой снимка и подписью ответственного.
3. CSV/JSON находок для ЦНИТ и для загрузки в задачник.

## 4. Стек

| Слой | Выбор |
|---|---|
| Язык | Python 3.12 |
| Обход | Playwright (рендер JS, axe-core), httpx (HEAD/GET), dnspython, sslyze/cryptography, python-whois |
| Разбор | lxml/BeautifulSoup, extruct (микроразметка), pdfplumber/pypdf, openpyxl |
| Подписи | openssl с gost-engine или КриптоПро CSP (проверка .sig) |
| Хранилище | PostgreSQL (находки, история), объектное хранилище/файловая система для снимков |
| LLM | Anthropic SDK (`anthropic`), Messages API со structured outputs, Batch API |
| Оркестрация | cron/systemd-таймеры на старте, затем Prefect |
| Отчёты | Jinja2 + ECharts (как в v2), WeasyPrint для PDF |
| Размещение | сервер в РФ с белым IP (иначе DDoS-Guard отдаёт 502) |

## 5. Ограничения и правовые рамки самой системы
- Только публичные данные и пассивные запросы; активные сканы — по разрешению.
- Не хранить ПДн сверх публично опубликованных; снимки страниц с ПДн (реестр ППС) хранить с ограниченным доступом.
- Отчёт остаётся внутренним рабочим документом, а не актом надзора; формулировки статусов сохраняются как в v2.
- LLM получает только публичный контент сайта, без внутренних документов вуза, пока не согласовано иное.

## 6. План внедрения

| Этап | Срок | Результат |
|---|---|---|
| 0. Каркас | 1 неделя | репозиторий, реестр проверок (YAML), схема находки, сборщик с хранением снимков |
| 1. Фронт A + E | 3–4 недели | 40 детерминированных проверок по №1493/№1802, ссылки ФГОС, .sig, генерация HTML-панели, воспроизводящей v2 из JSON |
| 2. Фронты B, C, D | 3 недели | axe-core, ПДн-чеклист, TLS/DNS/заголовки/чёрные списки/дефейс, алерты |
| 3. LLM-слой | 2–3 недели | чтение PDF, классификация дефектов, карточки «что делать», дельта |
| 4. Эксплуатация | постоянно | расписания, нормативный монитор, PDF-отчёт, подключение филиалов |
| 5. Тираж | по решению | несколько вузов на одной установке, сравнительная панель |

Первый полезный результат (этап 1) — через месяц: еженедельный отчёт по обязательному разделу с доказательствами и дельтой, без ручного счёта.
